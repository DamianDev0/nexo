# 2.1 — Objetos configurables

> Tamaño L · Depende de: [0. Preparación](README.md#0-preparación) · Habilita: 2.2, 2.3, 2.4, 2.5
> ADR a escribir: **ADR-0010 Metadata de objetos** (Proposed → Accepted antes del PR A1).

## Objetivo

Que cada tenant tenga un **modelo de datos declarado como metadata**: objetos estándar (contacto, empresa, negocio) y **objetos propios** (Inmuebles, Citas, Vehículos…) con campos tipados, relaciones con etiqueta, vistas, tablero y ficha generados desde esa metadata. Ningún objeto nuevo requiere código.

**Criterio de salida (uno solo):** un admin instala la plantilla "Inmuebles", la ve en el menú, crea 3 registros, los relaciona con contactos como "Propietario" y los filtra por un campo numérico — sin despliegue.

## Alcance

**Dentro**

- Tablas de metadata por tenant: objetos, campos, definiciones de relación.
- Migración de `config.customFields` (JSON público) a metadata por tenant, con capa de compatibilidad.
- Objetos propios almacenados en tabla genérica `records`.
- Relaciones con etiqueta entre cualquier par de objetos (estándar o propio).
- API REST genérica `/objects/...` derivada de metadata.
- Validador único de valores por tipo de campo.
- Compilador de filtros tipado para propiedades JSONB (arregla C7) + búsqueda sin tildes y teléfonos normalizados (C5, C6).
- Web: descriptor construido desde metadata, tablero y ficha genéricos, menú dinámico, Ajustes → Objetos (desde plantilla).
- Límites por plan y contadores visibles.

**Fuera (va a otro plan)**

- Pipelines/kanban en objetos → 2.3.
- Paquetes versionados completos → 2.4 (aquí solo se instala una **plantilla de objeto** mínima).
- Permisos por registro → posterior. Permisos **por campo ya existen** (`TenantFullConfig.fieldPermissions`): se migran a `field_definitions.config.permissions` y se respetan en la API genérica.
- `rollup`, `file`, `geolocation` → posterior. `formula` **ya existe** (`settings/services/custom-fields-computer.service.ts` + `shared/formula/formula.util.ts`): se reutiliza en objetos propios.
- Promover un objeto propio a tabla física → solo diseño (§4.4), sin implementar.

## Decisiones (contenido de ADR-0010)

| #   | Decisión                                                                                                                            | Alternativa descartada                | Por qué                                                                                                                                                           |
| --- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Metadata **dentro del schema del tenant** (`object_definitions`, `field_definitions`)                                               | Metadata central en `public` (Twenty) | Aislamiento natural (ADR-0001), backups por tenant, sin joins cross-schema. Cache en Redis por `tenantId:metadataVersion`                                         |
| D2  | Objetos propios en **una tabla genérica `records`** con `properties JSONB` + columnas comunes reales                                | DDL por objeto (Twenty)               | Sin migraciones por cambio de campo; volúmenes pyme (GoHighLevel limita 300k/objeto). Índices GIN + expresiones por campo filtrable                               |
| D3  | Objetos estándar **siguen en sus tablas** y se describen con `object_definitions.is_system = true`                                  | Migrar contactos a `records`          | Cero riesgo sobre Contactos; columnas y FKs existentes se mapean a `field_definitions` con `storage = 'column'`                                                   |
| D4  | Llave de objeto = `key` slug inmutable (`contact`, `company`, `deal`, `inmueble`)                                                   | UUID como tipo                        | Legible en URLs, vistas, eventos y paquetes; renombrar solo cambia `label_singular/plural`                                                                        |
| D5  | Relaciones en tabla `record_associations` + `association_definitions` con etiqueta pareada y cardinalidad                           | Columnas FK por relación              | Funciona entre cualquier par sin DDL. FKs estándar existentes (`contacts.company_id`, `deals.contact_id`) se exponen como asociaciones de sistema de solo lectura |
| D6  | `ObjectType` pasa de unión cerrada a `string` validado contra metadata                                                              | Mantener unión                        | Requisito para objetos propios. `object_views.object_type` pierde el CHECK y gana FK lógica validada en servicio                                                  |
| D7  | Un **validador de valores** compartido (`shared/object-engine/validation`) llamado desde API, import, bulk y (luego) automatización | Validación por módulo                 | Principio P3; HubSpot documenta huecos por no hacerlo                                                                                                             |
| D8  | Permisos v1 **por objeto y rol** (`min_role_view`, `min_role_edit`) + permisos por campo existentes migrados                        | Por registro ya                       | Suficiente para pymes; por registro en fase posterior                                                                                                             |

## 1. Modelo de datos

### 1.1 Migración `0049_object_metadata`

```sql
CREATE TABLE "${schema}".object_definitions (
  key             VARCHAR(63) PRIMARY KEY CHECK (key ~ '^[a-z][a-z0-9_]{1,62}$'),
  label_singular  VARCHAR(80)  NOT NULL,
  label_plural    VARCHAR(80)  NOT NULL,
  icon            VARCHAR(40)  NOT NULL DEFAULT 'cube',
  color           VARCHAR(100) NOT NULL DEFAULT '#6366F1',
  storage         VARCHAR(10)  NOT NULL CHECK (storage IN ('table','records')),
  primary_field   VARCHAR(63)  NOT NULL,
  is_system       BOOLEAN      NOT NULL DEFAULT false,
  is_active       BOOLEAN      NOT NULL DEFAULT true,
  position        INTEGER      NOT NULL DEFAULT 0,
  min_role_view   VARCHAR(20)  NOT NULL DEFAULT 'viewer',
  min_role_edit   VARCHAR(20)  NOT NULL DEFAULT 'sales_rep',
  source_package  VARCHAR(80),
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE TABLE "${schema}".field_definitions (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  object_key      VARCHAR(63) NOT NULL REFERENCES "${schema}".object_definitions(key),
  key             VARCHAR(63) NOT NULL CHECK (key ~ '^[a-z][a-z0-9_]{0,62}$'),
  label           VARCHAR(120) NOT NULL,
  type            VARCHAR(20)  NOT NULL,
  storage         VARCHAR(10)  NOT NULL CHECK (storage IN ('column','property')),
  column_name     VARCHAR(63),
  config          JSONB NOT NULL DEFAULT '{}',   -- options, min, max, placeholder, currency, relation
  is_required     BOOLEAN NOT NULL DEFAULT false,
  is_unique       BOOLEAN NOT NULL DEFAULT false,
  is_filterable   BOOLEAN NOT NULL DEFAULT true,
  is_sortable     BOOLEAN NOT NULL DEFAULT false,
  show_in_form    BOOLEAN NOT NULL DEFAULT true,
  group_key       VARCHAR(63),
  is_system       BOOLEAN NOT NULL DEFAULT false,
  is_active       BOOLEAN NOT NULL DEFAULT true,
  position        INTEGER NOT NULL DEFAULT 0,
  source_package  VARCHAR(80),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (object_key, key)
);

CREATE TABLE "${schema}".metadata_versions (
  id          INTEGER PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  version     BIGINT NOT NULL DEFAULT 1,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
INSERT INTO "${schema}".metadata_versions DEFAULT VALUES;
```

Seed en la misma migración: filas `is_system` para `contact`, `company`, `deal` (`storage = 'table'`) y sus campos estándar como `storage = 'column'` (fuente: `CONTACT_COLUMN_CATALOG`, columnas de `companies`/`deals` en `tenant-schema.sql.ts`).

### 1.2 Migración `0050_records_and_associations`

```sql
CREATE TABLE "${schema}".records (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  object_key     VARCHAR(63) NOT NULL REFERENCES "${schema}".object_definitions(key),
  name           VARCHAR(300) NOT NULL,
  properties     JSONB NOT NULL DEFAULT '{}',
  tags           TEXT[] NOT NULL DEFAULT '{}',
  assigned_to_id UUID REFERENCES "${schema}".users(id),
  pipeline_id    UUID REFERENCES "${schema}".pipelines(id),
  stage_id       UUID REFERENCES "${schema}".pipeline_stages(id),
  search_text    TEXT GENERATED ALWAYS AS (nexo_unaccent(lower(name || ' ' || properties::text))) STORED,
  is_active      BOOLEAN NOT NULL DEFAULT true,
  created_by     UUID REFERENCES "${schema}".users(id),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON "${schema}".records (object_key, is_active, created_at DESC, id);
CREATE INDEX ON "${schema}".records USING GIN (properties jsonb_path_ops);
CREATE INDEX ON "${schema}".records USING GIN (search_text gin_trgm_ops);
CREATE INDEX ON "${schema}".records (object_key, stage_id) WHERE is_active;

CREATE TABLE "${schema}".association_definitions (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  from_object    VARCHAR(63) NOT NULL REFERENCES "${schema}".object_definitions(key),
  to_object      VARCHAR(63) NOT NULL REFERENCES "${schema}".object_definitions(key),
  key            VARCHAR(63) NOT NULL,
  label          VARCHAR(80) NOT NULL,          -- "Propietario"
  inverse_label  VARCHAR(80) NOT NULL,          -- "Inmueble de"
  cardinality    VARCHAR(10) NOT NULL CHECK (cardinality IN ('one_one','one_many','many_many')),
  max_per_record INTEGER CHECK (max_per_record BETWEEN 1 AND 1000),
  is_system      BOOLEAN NOT NULL DEFAULT false,
  source_package VARCHAR(80),
  UNIQUE (from_object, to_object, key)
);

CREATE TABLE "${schema}".record_associations (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  definition_id  UUID NOT NULL REFERENCES "${schema}".association_definitions(id),
  from_id        UUID NOT NULL,
  to_id          UUID NOT NULL,
  created_by     UUID REFERENCES "${schema}".users(id),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (definition_id, from_id, to_id)
);
CREATE INDEX ON "${schema}".record_associations (definition_id, from_id);
CREATE INDEX ON "${schema}".record_associations (definition_id, to_id);
```

- `nexo_unaccent` = función `IMMUTABLE` que envuelve `unaccent` (requerida para columnas generadas). Se crea en `public` con `CREATE EXTENSION IF NOT EXISTS unaccent` y se reutiliza para contactos (C5).
- `from_id`/`to_id` sin FK porque apuntan a tablas distintas según objeto: la integridad la garantiza el servicio (existe, activo, mismo tenant) + limpieza en archivado definitivo.

### 1.3 Migración `0051_object_views_any_type`

```sql
ALTER TABLE "${schema}".object_views DROP CONSTRAINT object_views_object_type_check;
ALTER TABLE "${schema}".object_workspace_states DROP CONSTRAINT object_workspace_states_object_type_check;
ALTER TABLE "${schema}".object_views ALTER COLUMN object_type TYPE VARCHAR(63);
ALTER TABLE "${schema}".object_workspace_states ALTER COLUMN object_type TYPE VARCHAR(63);

### 1.4 Migración de campos custom `0052_field_definitions_from_config`

No es SQL puro: script de datos idempotente en `TenantMigrationService` (lee `public.tenants.config.customFields` del tenant y hace upsert en `field_definitions` con `storage = 'property'`). Después:

- `TenantConfigService.getCustomFields` lee de `field_definitions` y devuelve la misma forma `CustomFieldsConfig` (compatibilidad para `/settings/custom-fields/:entity`, import y formularios).
- `config.customFields` queda de solo lectura una versión; se elimina en 2.4.

                records.controller.ts · record-views.controller.ts · record-workspace.controller.ts

  mappers/      object-definition.mapper.ts · field-definition.mapper.ts · record.mapper.ts
  dto/  interfaces/  constants/ (object-templates/*.ts)  events/
```

Motor compartido nuevo en `apps/api/src/shared/object-engine/`:

- `metadata/` — `ObjectMetadataService` (lectura + cache), `ObjectDefinitionsWriter`, `FieldDefinitionsWriter`, `AssociationDefinitionsWriter` y sus repositorios. Viven en `shared` (no en `modules/objects`) porque `industry-packs` (2.4) y `pipelines` (2.3) deben escribir metadata sin importar otro módulo (ADR-0004). `modules/objects` expone HTTP y orquesta.
- `validation/field-value.validator.ts` — valida y normaliza un valor según `FieldDefinition` (tipo, requerido, opciones, min/max, moneda en centavos, teléfono CO, email, fecha ISO). Devuelve `{ value, error }`.
- `sql/property-filter-sql.ts` — cláusulas tipadas sobre `properties->>'key'` con cast por tipo (`::numeric`, `::date`, `::boolean`, `@>` para multiselect).
- `definitions/metadata-table-definition.ts` — construye `ObjectTableDefinition` + `RecordFilterDefinition` desde metadata.

Rutas de Contactos existentes **no cambian**. `/objects/contact/*` responde solo lectura de metadata en esta fase.

### 2.3 Servicios clave

- **`ObjectMetadataService`**: `get(schema, tenantId)` → snapshot `{ version, objects, fields, associations }` cacheado en Redis `metadata:{tenantId}:{version}`; toda escritura de metadata incrementa `metadata_versions.version` en la misma transacción.
- **`RecordsService`**: resuelve definición, aplica límites de registros, valida (`FieldValueValidator`), unicidad (`properties->>key` con índice parcial creado bajo demanda al marcar `is_unique`), emite eventos.
- **Controladores dinámicos de vistas/workspace**: subclases que resuelven `definition` por request desde `ObjectMetadataService` (hoy `definition` es propiedad estática; añadir método protegido `resolveDefinition(ctx, params)` en los base controllers de ADR-0009).

### 2.4 Eventos

Agregar a `WEBHOOK_EVENTS` (`packages/shared-types/src/webhooks.ts`): `record.created`, `record.updated`, `record.archived`, `record.restored`, `association.created`, `association.deleted`, `object.created`, `object.updated`. Payload siempre con `objectKey`.

## 4. Rendimiento, seguridad y operación

1. **Presupuestos p95** (nuevo `apps/api/test/perf/records.perf-spec.ts`, 100k registros en un objeto): lista 120 ms · filtro numérico 150 ms · búsqueda sin tildes 180 ms · crear 60 ms.
2. **Índices por campo filtrable:** al marcar `is_filterable` en tipos number/date se crea índice de expresión `((properties->>'key')::numeric)` con `CREATE INDEX CONCURRENTLY` en job BullMQ (fuera de la transacción de metadata); estado visible en Ajustes.
3. **Aislamiento:** e2e cross-tenant para cada endpoint de §2.2 (`apps/api/test/objects-isolation.e2e-spec.ts`, `records-isolation`, `associations-isolation`).
4. **Promoción futura (solo diseño):** si un objeto supera `recordsPerCustomObject` de Business, se promueve a tabla física con DDL generado desde metadata (patrón Twenty). No se implementa en 2.1.
5. **Inyección:** claves de campo validadas por regex antes de interpolarse en expresiones JSONB; valores siempre `$n`.
