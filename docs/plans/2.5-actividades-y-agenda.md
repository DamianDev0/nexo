# 2.5 — Actividades y agenda sobre cualquier registro

> Tamaño M/L · Depende de: 2.1 (A1, A4, B4) · Paralelo con 2.2 y 2.3
> ADR a escribir: **ADR-0013 Actividades polimórficas**.

## Objetivo

Que tareas, llamadas, reuniones, notas y visitas se registren sobre **cualquier registro** (contacto, empresa, negocio, cita, inmueble…), que cada vendedor tenga **"Mis tareas"** como pantalla de trabajo diario, un **calendario** en hora de Bogotá con festivos colombianos, **recordatorios** confiables, y que **"sin próximo paso"** sea un estado visible y filtrable en cualquier objeto.

**Criterio de salida (el de Fase 2):** un vendedor gestiona su semana completa sin salir de Nexo: abre "Mis tareas" (hoy/vencidas/próximas), completa 3, agenda una visita a un inmueble desde su ficha, recibe el recordatorio, y filtra en Negocios "sin próximo paso".

## Decisiones (ADR-0013)

| #   | Decisión                                                                                                                                                                                                   | Por qué                                                                        |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| D1  | Tabla `activity_links (activity_id, object_key, record_id, is_primary)`; una actividad puede enlazar varios registros (reunión con contacto + negocio + inmueble)                                          | Funciona con objetos propios sin FKs nuevas                                    |
| D2  | Las FKs `contact_id/company_id/deal_id` se mantienen **escritas en paralelo** una versión y luego pasan a vista de compatibilidad                                                                          | Contactos y reportes existentes no se rompen                                   |
| D3  | `next_activity_due` y `last_activity_at` **denormalizados** en `contacts`, `companies`, `deals`, `records`, mantenidos por un listener de eventos de actividad dentro de la misma transacción de escritura | Filtros y orden rápidos en tableros de 50k+                                    |
| D4  | "Sin próximo paso" = registro activo, en etapa `open` (si tiene pipeline), sin actividad pendiente futura, con `last_activity_at` más viejo que `no_next_step_days` de la metadata del objeto (default 7)  | Umbral configurable por objeto y por paquete (P4)                              |
| D5  | Festivos en `packages/shared-utils/src/holidays-co.ts` calculados (Ley Emiliani + Pascua), no tabla                                                                                                        | Sin mantenimiento anual; usado por calendario y Fase 5                         |
| D6  | Recordatorios con BullMQ delayed jobs idempotentes por `activity_id:reminder_at`; al cambiar hora se reemplaza el job                                                                                      | Nada falla en silencio (P8): job fallido deja notificación de error al creador |
| D7  | Timeline por registro servido por el módulo `timeline` para todo objeto; `GET /contacts/:id/timeline` delega                                                                                               | Cierra I16                                                                     |

## 1. Modelo de datos

### Migración `0056_activity_links`

```sql
CREATE TABLE "${schema}".activity_links (
  activity_id UUID NOT NULL REFERENCES "${schema}".activities(id) ON DELETE CASCADE,
  object_key  VARCHAR(63) NOT NULL REFERENCES "${schema}".object_definitions(key),
  record_id   UUID NOT NULL,
  is_primary  BOOLEAN NOT NULL DEFAULT false,
  PRIMARY KEY (activity_id, object_key, record_id)
);
CREATE INDEX ON "${schema}".activity_links (object_key, record_id);

INSERT INTO "${schema}".activity_links (activity_id, object_key, record_id, is_primary)
  SELECT id, 'contact', contact_id, true FROM "${schema}".activities WHERE contact_id IS NOT NULL
  UNION ALL SELECT id, 'company', company_id, contact_id IS NULL FROM "${schema}".activities WHERE company_id IS NOT NULL
  UNION ALL SELECT id, 'deal', deal_id, contact_id IS NULL AND company_id IS NULL FROM "${schema}".activities WHERE deal_id IS NOT NULL
ON CONFLICT DO NOTHING;

ALTER TABLE "${schema}".companies ADD COLUMN IF NOT EXISTS next_activity_due TIMESTAMPTZ, ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ;
ALTER TABLE "${schema}".deals     ADD COLUMN IF NOT EXISTS next_activity_due TIMESTAMPTZ, ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ;
ALTER TABLE "${schema}".records   ADD COLUMN IF NOT EXISTS next_activity_due TIMESTAMPTZ, ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ;
ALTER TABLE "${schema}".contacts  ADD COLUMN IF NOT EXISTS last_activity_at TIMESTAMPTZ;

CREATE INDEX ON "${schema}".activities (assigned_to_id, status, due_date) WHERE is_active;
CREATE INDEX ON "${schema}".activities (reminder_at) WHERE is_active AND status = 'pending' AND reminder_at IS NOT NULL;

ALTER TABLE "${schema}".object_definitions
  ADD COLUMN IF NOT EXISTS no_next_step_days INTEGER NOT NULL DEFAULT 7 CHECK (no_next_step_days BETWEEN 1 AND 180);
```

Backfill de `next_activity_due`/`last_activity_at` en job por tenant (no en migración).

## 5. Pruebas clave

- **Zona horaria:** tarea con `due_date` 23:30 Bogotá cae en "hoy" y no en "mañana" (UTC 04:30).
- **Festivos:** 2026-01-12 (Reyes trasladado), Semana Santa, 2026-08-17 (Asunción trasladada).
- **Denormalización:** completar la única tarea pendiente de un negocio → `next_activity_due = NULL` y aparece en "sin próximo paso" tras el umbral.
- **Polimorfismo:** una reunión enlazada a contacto + negocio + inmueble aparece en los 3 timelines y actualiza los 3 denormalizados.
- **Aislamiento:** links a `record_id` de otro tenant → 404.

## 6. Riesgos

| Riesgo                                  | Mitigación                                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------------------ |
| Denormalizados desincronizados          | Recalcular por registro en la misma transacción + job nocturno de verificación con reporte |
| Escritura dual FKs/links diverge        | Test de consistencia en CI y fecha fija para retirar FKs (siguiente épica)                 |
| Recordatorios duplicados tras reinicios | Job id determinístico `activity:{id}:{reminderAt}`                                         |
| Calendario pesado                       | Rango máximo 6 semanas por consulta, índices `(assigned_to_id, status, due_date)`          |
