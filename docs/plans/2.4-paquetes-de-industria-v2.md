# 2.4 — Paquetes de industria v2

> Tamaño M · Depende de: 2.1 (A1–A5), 2.3 (P2, P4) · Reemplaza: `applyPreset` actual
> ADR a escribir: **ADR-0011 Paquetes de industria versionados**.

## Objetivo

Convertir los presets (que hoy **renombran** y siembran campos una sola vez) en **paquetes versionados e instalables**: un manifiesto declara objetos, campos, relaciones, pipelines, vistas, taxonomías, etiquetas, plantillas de mensaje, tablero inicial y automatizaciones (declaradas, inactivas hasta Fase 5). Instalar, actualizar y revertir sin tocar datos del cliente y sin consultor.

**Criterio de salida:** un dueño de inmobiliaria crea su cuenta, elige "Inmobiliaria", ve en una pantalla qué se va a crear, instala en < 10 min de onboarding total, y cuando publicamos la versión 1.1 del paquete ve un diff, acepta, y sus campos personalizados propios quedan intactos. Puede revertir la actualización.

## Decisiones (ADR-0011)

| #   | Decisión                                                                                                                                                                                                | Por qué                                                                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| D1  | Paquetes como **archivos TypeScript tipados en el repo** (`packages/industry-packs/<key>/<version>.ts`), publicados a `public.industry_packages` al desplegar                                           | Revisión en PR, tests, versionado con git; sin editor en producción todavía |
| D2  | **Configuración, nunca datos** (P2): el manifiesto no puede declarar registros                                                                                                                          | Igual que GoHighLevel excluye contactos/conversaciones                      |
| D3  | Instalación = **plan** (diff calculado) → **confirmación** → **aplicación en una transacción** → registro de instalación con snapshot previo                                                            | Rollback posible (lo que a GoHighLevel le falta)                            |
| D4  | Cada elemento creado lleva `source_package = '<key>@<version>'`; el cliente puede editarlo y queda marcado `customized`                                                                                 | Merge por elemento en actualizaciones                                       |
| D5  | Reglas de merge en actualización: **agregar** lo nuevo, **actualizar** solo elementos no personalizados, **nunca borrar** (se proponen como "obsoletos" para que el admin archive), conflictos listados | Protege el trabajo del cliente                                              |
| D6  | Un tenant tiene **un paquete principal** y N **complementos** (p. ej. "Cartera", "Postventa")                                                                                                           | Composición sin fragmentar el producto (foundations §5)                     |
| D7  | Los 9 presets actuales se convierten en manifiestos `@1.0.0` equivalentes; `applyPreset` se elimina                                                                                                     | Una sola vía                                                                |
| D8  | `industry-packs` escribe metadata con los writers de `shared/object-engine/metadata` (2.1) y pipelines con `shared/object-engine/pipelines` (mover `PipelinesWriter` ahí en 2.3 P2). No importa módulos | Respeta ADR-0004 sin sumar excepciones a `CROSS_MODULE_ALLOWED`             |

## 1. Manifiesto

`packages/industry-packs/src/manifest.types.ts` (paquete nuevo del monorepo, exporta tipos y catálogo; validación con zod compartido por api y web):

```ts
export type IndustryPackManifest = {
  key: string // 'inmobiliaria'
  version: `${number}.${number}.${number}`
  kind: 'primary' | 'addon'
  sector: IndustrySector | null
  name: string // 'Inmobiliaria'
  summary: string // una frase para el selector
  requires?: Array<{ key: string; range: string }>
  lexicon: {
    // capa 1
    nomenclature: Partial<TenantNomenclature>
    iconPack?: string
  }
  structure: {
    // capa 2
    objects: ObjectDefinitionSpec[] // 2.1 §1.1
    fields: FieldDefinitionSpec[] // también para contact/company/deal
    associations: AssociationDefinitionSpec[]
    pipelines: PipelineSpec[] // 2.3 §1 (con stage_type, required_fields)
    taxonomies: {
      contactLifecycle?: TaxonomyOption[]
      contactSources?: TaxonomyOption[]
      lostReasons?: SelectOption[]
    }
    tags: Array<{ name: string; color: string; entity: string }>
    views: ObjectViewSpec[] // table/board, compartidas
  }
  behavior: {
    // capa 3 (declarado; ejecutable en Fase 5)
    messageTemplates: MessageTemplateSpec[]
    automations: AutomationSpec[] // enabled: false hasta Fase 5
  }
  home: {
    // pregunta 5: "¿qué número miras cada mañana?"
    dashboard: DashboardWidgetSpec[]
  }
  onboarding: {
    questions?: OnboardingQuestion[] // p. ej. "¿Arriendas, vendes o ambos?" → activa pipelines
    checklist: string[] // primeros pasos sugeridos
  }
}
```

Validaciones del manifiesto (test por paquete en CI):

- Toda referencia (`object_key`, `field key`, `pipeline`, `association`) existe dentro del paquete o en objetos de sistema.
- Respeta límites del plan más bajo que lo ofrece (2.1 §1.5).
- Textos es-CO sin género forzado donde interpolan nomenclatura (P9).
- Sin `if (industry)` en código: todo lo específico vive aquí (P4).

## 2. Modelo de datos

### Público (catálogo)

```sql
CREATE TABLE public.industry_packages (
  key          VARCHAR(80) NOT NULL,
  version      VARCHAR(20) NOT NULL,
  kind         VARCHAR(10) NOT NULL,
  manifest     JSONB NOT NULL,
  checksum     CHAR(64) NOT NULL,
  published_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  is_latest    BOOLEAN NOT NULL DEFAULT false,
  PRIMARY KEY (key, version)
);
```

### Tenant — migración `0055_package_installs`

```sql
CREATE TABLE "${schema}".package_installs (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  package_key     VARCHAR(80) NOT NULL,
  from_version    VARCHAR(20),
  to_version      VARCHAR(20) NOT NULL,
  status          VARCHAR(15) NOT NULL CHECK (status IN ('planned','applied','failed','rolled_back')),
  plan            JSONB NOT NULL,         -- diff calculado
  before_snapshot JSONB,                  -- metadata previa de los elementos tocados
  error           TEXT,
  applied_by      UUID REFERENCES "${schema}".users(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  applied_at      TIMESTAMPTZ
);
```

Elementos de metadata (`object_definitions`, `field_definitions`, `association_definitions`, `pipelines`, `object_views`, `tags`, `message_templates`) ya tienen o reciben `source_package` + `customized BOOLEAN NOT NULL DEFAULT false` (se marca en cualquier edición del admin).

## 3. Motor de instalación

Módulo `apps/api/src/modules/industry-packs`:

| Servicio                 | Responsabilidad                                                                                                                                                                                                                                 |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PackageCatalogService`  | Lee `public.industry_packages`, resuelve `latest`, compatibilidad con plan                                                                                                                                                                      |
| `PackagePlannerService`  | `plan(tenant, key, version)` → `PackagePlan { create[], update[], obsolete[], conflicts[], limitViolations[] }` comparando manifiesto vs metadata actual + `source_package` + `customized`                                                      |
| `PackageApplierService`  | Aplica un plan en **una transacción** con los writers de `shared/object-engine` (D8) y `TenantConfigService` de `settings` (lectura/escritura de nomenclatura permitida por ADR-0008), guarda `before_snapshot`, incrementa `metadata_versions` |
| `PackageRollbackService` | Revierte la última instalación `applied` si ningún elemento creado tiene datos (p. ej. objeto con registros → se archiva en vez de borrar; se informa)                                                                                          |

Endpoints:

| Método | Ruta                                           | Rol                                                       |
| ------ | ---------------------------------------------- | --------------------------------------------------------- |
| GET    | `/industry-packs`                              | owner/admin — catálogo con versión instalada y disponible |
| POST   | `/industry-packs/:key/plan`                    | admin — `{ version, answers }` → plan                     |
| POST   | `/industry-packs/installs/:installId/apply`    | admin — aplica plan `planned` (expira en 30 min)          |
| POST   | `/industry-packs/installs/:installId/rollback` | owner                                                     |
| GET    | `/industry-packs/installs`                     | admin — historial con estado y error (P8)                 |

Eventos: `package.installed`, `package.updated`, `package.rolled_back`, `package.failed`.

## 7. Pruebas clave

- **P2 (configuración ≠ datos):** instalar, actualizar y revertir no cambia `COUNT(*)` de `contacts`, `companies`, `deals`, `records`, `activities`.
- **Idempotencia:** aplicar el mismo plan dos veces no duplica nada.
- **Fallo a mitad:** error inyectado en el applier → transacción revertida, instalación `failed` con error legible (P8).
- **Aislamiento:** `/industry-packs/installs/*` de tenant A → 404 en B.
- **Límites:** paquete que excede límites del plan → plan con `limitViolations` y apply bloqueado.

## 8. Riesgos

| Riesgo                                                       | Mitigación                                                             |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Rollback imposible cuando ya hay datos en objetos creados    | Rollback archiva en lugar de borrar y lo informa; nunca pierde datos   |
| Paquetes divergen de la metadata real por ediciones manuales | `customized` + plan muestra conflictos explícitos                      |
| Contenido de paquetes mediocre = valor percibido bajo        | Validar cada paquete con 2 clientes reales del sector antes de `1.1.0` |
| Tentación de lógica por industria en código                  | Regla P4 con grep en CI; toda variación va al manifiesto               |
