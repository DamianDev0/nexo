# 2.3 — Pipelines en cualquier objeto

> Tamaño L · Depende de: 2.1 (A1, A4) · Paralelo con 2.2 y 2.5 · Habilita: 2.4
> ADR a escribir: **ADR-0012 Pipelines genéricos y reglas por etapa**.

## Objetivo

Que **cualquier objeto** (Negocios, Citas, Inmuebles, Órdenes de servicio…) tenga uno o varios pipelines con etapas, **reglas por etapa** (campos obligatorios, tipo abierta/ganada/perdida, días de estancamiento), **vista kanban** con arrastrar y soltar, historial de etapas genérico y, para Negocios, pronóstico ponderado en COP.

**Criterio de salida:** en un tenant de salud, el objeto "Citas" tiene un pipeline Solicitada → Confirmada → Atendida / No asistió; mover una cita a "Atendida" exige llenar "Profesional"; el kanban de Negocios muestra totales y pronóstico en COP correctos al centavo.

## Alcance

**Dentro:** pipelines con `object_key`, reglas por etapa, motivo de pérdida como opción configurable, vista tipo tablero en `object_views`, endpoint de tablero genérico paginado por etapa, movimiento de etapa genérico con validación, historial genérico y tiempos por etapa, kanban web con DnD accesible, pronóstico de negocios, cierre de money fixes de Fase 1, eventos `record.stage_changed`.

**Fuera:** automatizaciones por etapa (solo el evento y la configuración vacía `stage_hooks`), productos/líneas de negocio con IVA (Fase Dinero), reportes de embudo avanzados.

## Decisiones (ADR-0012)

| #   | Decisión                                                                                                                                   | Por qué                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| D1  | `pipelines.object_key` (default `deal`) y `records.pipeline_id/stage_id` (ya en 2.1)                                                       | Un solo modelo para todos los objetos                                            |
| D2  | `pipeline_stages.stage_type` ∈ `open`/`won`/`lost`; `deals.status` se **deriva** de la etapa al moverse                                    | Elimina estados desincronizados; mismo patrón que HubSpot Open/Closed            |
| D3  | `pipeline_stages.required_fields TEXT[]` validado en servidor con `FieldValueValidator` (2.1 D7)                                           | Blueprint simple, un solo punto de validación (P3)                               |
| D4  | `record_stage_history` genérica; `deal_stage_history` se mantiene y se escribe en ambas durante una versión, luego vista de compatibilidad | Sin romper reportes existentes                                                   |
| D5  | Vista tablero = `object_views.view_type = 'board'` + `board_config JSONB` (pipeline, campos de tarjeta, totales)                           | Reutiliza guardado/compartido/orden de vistas (ADR-0009)                         |
| D6  | DnD **sin librería nueva**: pointer events + `motion` (ya instalado) con teclado obligatorio ("Mover a etapa" en menú de tarjeta y atajos) | `@dnd-kit` está marcado como dependencia muerta; reintroducirlo exige ADR aparte |
| D7  | Movimiento optimista con TanStack Query + rollback, alineado con `useOptimisticRecordListPatch`                                            | Defaults del frontend permiten TanStack para kanban DnD                          |
| D8  | Motivos de pérdida = `TaxonomyOption[]` por objeto, editados con el `TaxonomyPane` existente (con reasignación al retirar una opción)      | Reutiliza UI y patrón de taxonomías de contactos; configurable por paquete       |

## 1. Modelo de datos

### Migración `0054_generic_pipelines`

```sql
ALTER TABLE "${schema}".pipelines
  ADD COLUMN IF NOT EXISTS object_key  VARCHAR(63) NOT NULL DEFAULT 'deal'
      REFERENCES "${schema}".object_definitions(key),
  ADD COLUMN IF NOT EXISTS position    INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS is_active   BOOLEAN NOT NULL DEFAULT true,
  ADD COLUMN IF NOT EXISTS source_package VARCHAR(80);

ALTER TABLE "${schema}".pipeline_stages
  ADD COLUMN IF NOT EXISTS stage_type      VARCHAR(10) NOT NULL DEFAULT 'open'
      CHECK (stage_type IN ('open','won','lost')),
  ADD COLUMN IF NOT EXISTS required_fields TEXT[] NOT NULL DEFAULT '{}',
  ADD COLUMN IF NOT EXISTS rotting_days    INTEGER CHECK (rotting_days BETWEEN 1 AND 365),
  ADD COLUMN IF NOT EXISTS stage_hooks     JSONB NOT NULL DEFAULT '{}',
  ADD COLUMN IF NOT EXISTS is_active       BOOLEAN NOT NULL DEFAULT true;

CREATE UNIQUE INDEX IF NOT EXISTS "uq_${schema}_pipelines_default_per_object"
  ON "${schema}".pipelines (object_key) WHERE is_default AND is_active;

CREATE TABLE IF NOT EXISTS "${schema}".record_stage_history (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  object_key      VARCHAR(63) NOT NULL,
  record_id       UUID NOT NULL,
  pipeline_id     UUID NOT NULL REFERENCES "${schema}".pipelines(id),
  from_stage_id   UUID REFERENCES "${schema}".pipeline_stages(id),
  to_stage_id     UUID NOT NULL REFERENCES "${schema}".pipeline_stages(id),
  seconds_in_from BIGINT,
  changed_by      UUID REFERENCES "${schema}".users(id),
  changed_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON "${schema}".record_stage_history (object_key, record_id, changed_at DESC);

ALTER TABLE "${schema}".object_views
  ADD COLUMN IF NOT EXISTS view_type    VARCHAR(10) NOT NULL DEFAULT 'table' CHECK (view_type IN ('table','board')),
  ADD COLUMN IF NOT EXISTS board_config JSONB;

ALTER TABLE "${schema}".deals
  ADD COLUMN IF NOT EXISTS stage_entered_at TIMESTAMPTZ;
UPDATE "${schema}".pipeline_stages s SET stage_type = 'won'
  WHERE lower(s.name) IN ('ganado','cerrado ganado','won');
UPDATE "${schema}".pipeline_stages s SET stage_type = 'lost'
  WHERE lower(s.name) IN ('perdido','cerrado perdido','lost');
```

- Backfill de `record_stage_history` desde `deal_stage_history` en job, no en migración.
- `records` recibe `stage_entered_at` en la misma migración.

## 2. API

### 2.1 Dónde vive

- Escritura de pipelines/etapas en `shared/object-engine/pipelines/` (`PipelinesWriter` + repositorio) para que `industry-packs` (2.4) la reutilice sin importar módulos.
- Módulo `pipelines` nuevo (sale de `settings`): `controllers/pipelines.controller.ts`, `services/pipelines.service.ts`, `services/stage-transition.service.ts`, `repositories/pipelines.repository.ts`, `repositories/stage-history.repository.ts`, `mappers/*`. `settings/controllers/pipeline.controller.ts` delega durante una versión y se elimina.
- `StageTransitionService` es el **único** camino para cambiar etapa: valida pipeline del objeto, etapa activa, `required_fields` con el validador, deriva estado (`won`/`lost`/`open`), escribe historial, emite eventos. `deals.service.ts` `stage/won/lost/reopen` lo llaman.

### 2.2 Endpoints

| Método            | Ruta                                               | Notas                                                                                                                                             |
| ----------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET               | `/pipelines?objectKey=deal`                        | Con etapas, reglas y conteos                                                                                                                      |
| POST/PATCH/DELETE | `/pipelines[/:id]`                                 | Admin; borrar exige mover registros o archivar                                                                                                    |
| PATCH             | `/pipelines/:id/stages`                            | Reordenar, crear, editar reglas; etapa con registros no se borra, se archiva                                                                      |
| GET               | `/objects/:key/board?pipelineId&viewId&...filters` | Columnas con `count`, `totalCents` (si el objeto tiene campo monetario marcado `board_total`), primeras N tarjetas por etapa y cursor por columna |
| GET               | `/objects/:key/board/:stageId/cards?cursor`        | Paginación infinita por columna                                                                                                                   |
| PATCH             | `/objects/:key/records/:id/stage`                  | `{ stageId, fields?, lostReason? }` → 422 `{ missingFields: [...] }` si faltan requeridos                                                         |
| GET               | `/objects/:key/records/:id/stage-history`          | Con tiempo por etapa                                                                                                                              |
| GET               | `/deals/forecast?pipelineId&from&to&ownerId`       | Suma ponderada por mes de cierre esperado, en centavos                                                                                            |

### 2.3 Eventos

`record.stage_changed` (`objectKey`, `recordId`, `fromStageId`, `toStageId`, `stageType`) además de `deal.stage_changed/won/lost` existentes. `stage_hooks` queda como punto de enganche para Fase 5.

### 2.4 Money fixes de Fase 1 (PR P1)

- `deals` DTO: `valueCents` entero (`@IsInt`, `@Min(0)`), rechazar decimales.
- `pipeline-settings.repository.ts:175`: sumas como `::text` + `toCents` (ya parcial) y test de coerción.
- `products` bind-param bug (ver ROADMAP): corregir y test.
- Todos los tests de dinero con `Number.isInteger`.

## 5. Pruebas

- **Unit:** derivación de estado por `stage_type`; validación de requeridos por tipo; cálculo de `seconds_in_from`; pronóstico ponderado con probabilidad de etapa u `probability_override`.
- **Concurrencia:** dos usuarios mueven la misma tarjeta → último gana, historial con ambas transiciones, sin estado inconsistente.
- **e2e:** mover negocio a etapa `lost` sin motivo → 422; con motivo → evento `deal.lost` y `record.stage_changed`.
- **Web:** `useDragToColumn` (pointer + teclado), rollback optimista, anuncio accesible.
- **Regresión:** Contactos journey; `deals-isolation.e2e-spec.ts` existente.

## 6. Riesgos

| Riesgo                                                       | Mitigación                                                                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| DnD propio con bugs de accesibilidad o scroll                | Hook aislado con tests, teclado obligatorio, fallback "Mover a etapa" en menú; si no cumple presupuesto, ADR para reintroducir `@dnd-kit` |
| Datos existentes con `deals.status` incoherente con la etapa | Script de reconciliación antes de P2 con reporte por tenant                                                                               |
| Tableros grandes                                             | Paginación por columna + conteos agregados en una sola consulta                                                                           |
| `deal_stage_history` y `record_stage_history` divergen       | Escritura dual en la misma transacción una versión; test que compara ambas                                                                |
